# 実行ファイルサイズ

ExecSandboxは「単一バイナリ完結」がコアコンセプト（仕様書§1）。サイズの最小化を
積極的に追求する必要はないが、**むやみに肥大化する実装は避ける**こと。

## ExecSandbox固有の増幅構造

ExecDBと決定的に違うのは、**本体のサイズ増加が6倍に増幅される**点である。

```
本体（cmd/execsandbox）に依存を1つ追加
  → 6環境分すべてのベースバイナリが増える
  → ビルダーがそれを全部同梱する（仕様書§6.3）
  → ビルダーの配布サイズが「増加分 × 6」増える
```

ビルダーは既に50MB規模（10MB前後 × 6環境）になる見込みであり
（仕様書§6.3）、ここに上乗せすると利用者のダウンロード体験に直結する。

**「本体に1MB足す」は「ビルダーに6MB足す」と読み替えて判断すること。**

## どこに置くかで重みが違う

| 置き場所 | サイズ影響 |
| :--- | :--- |
| `sandbox/`・`cmd/execsandbox/` | **6倍に増幅される。最も慎重に。** |
| `cmd/execsandbox-build/` | ビルダー自身のみ。1倍 |
| （SDKライブラリ） | 別リポジトリ。ゲスト側のWASMサイズに影響する |
| `tests/`・`testdata/` | 配布物に含まれない。自由 |

ビルダー側のコードは1倍にしか効かないため、本体に置く必要がない処理は
ビルダーへ寄せるという判断もありうる。

## 判断の目安

- 新しい依存ライブラリを追加する前に、標準ライブラリだけで実現できないかを
  一度検討すること。`wazero` 自体が「依存ゼロ」を掲げているライブラリであり、
  その上に重い依存を積むのは方針として整合しない。
- 依存を追加する場合、そのライブラリ自体のサイズだけでなく、推移的依存
  （transitive dependencies）がどれだけ増えるかも考慮すること。
- 色付け・罫線・TUI等の装飾ライブラリは導入しない（`cli-output.md` 参照）。
  典型的な「むやみな肥大化」の例。
- CLIパーサも、標準の `flag` パッケージで足りるなら外部ライブラリを入れない。
  仕様書§7.1のオプション体系（短形＋長形、繰り返し指定、`--` 終端）が
  標準 `flag` で書けるかはフェーズ①で確認する。書けない場合のみ検討する。

## ゲスト側のサイズ

SDKライブラリは別リポジトリ（`execsandbox-sdk`）にあるため、本リポジトリの
配布物サイズには影響しない。ただし本リポジトリの `testdata/modules/` に置く検証用
モジュールも、肥大化するとテストが遅くなる。

ゲスト側で標準ライブラリの重い部分（`fmt` の完全な機能、`reflect` 等）に依存すると、
TinyGoでもWASMサイズが跳ね上がる点は共通する。検証用モジュールは1つ1目的で小さく
保つこと（`.claude/rules/testing.md`）。

## 優先度

サイズ最適化そのものを目的化しない。まず正しく動くこと、仕様書に忠実であることを
優先し、その上で「同じ機能を実現するのに不必要に重い依存を選んでいないか」を
都度意識する、という程度のバランスでよい。
