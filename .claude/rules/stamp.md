# スタンプ方式（WASMモジュールの埋め込み）

生成される実行ファイルは、ベースバイナリの末尾にWASMモジュールとフッターを
追記したものである（仕様書§6.2）。ここでは実装上の具体を定める。

先行するExecDBが同じ「自分自身の末尾からデータを読む」仕組みをPoCで検証済みで
あり、**読み出し側はほぼそのまま流用できる**。一方、書き込み側は事情が大きく
異なる（後述）。

## フッター構造

ExecDBのPoCで実証された固定32バイトのレイアウトを踏襲する。

```
[ベースバイナリ][WASMモジュール][フッター(32バイト)]

フッター = Magic(8) + Version(4) + Offset(8) + Length(8) + Reserved(4)
```

- **整数はすべてビッグエンディアン。** ExecDBと揃える（フレーミングの長さ
  プレフィックスがリトルエンディアンなのは、WASM線形メモリの表現に合わせる
  ためであり、別の理由に基づく。混同しないこと）。
- **Magic** は8バイトの固定文字列。ExecDBは `EXECDB01` を使っていた。
  ExecSandboxでは別の文字列を使うこと（`EXECSB01` 等）。
- **Version** はフッター形式自体のバージョン。将来レイアウトを変えたときに
  古い実行ファイルを判別するために持つ。**現時点で使い道がなくても削らないこと。**
- **Offset** はWASMモジュールの開始位置。`ファイルサイズ - 32 - Length` で
  計算できるため厳密には冗長だが、ExecDBと構造を揃える意味と、将来
  複数ブロックを持つ拡張余地のため残す。
- **Reserved** はゼロ埋め。

## 読み出し（本体側）

起動時、`os.Executable()` で自身のパスを得て開き、末尾32バイトを `ReadAt` で
読む。

- **ファイルサイズがフッターサイズ未満なら、マジックの照合を試みない。**
  `ReadAt` が範囲外になる。
- **マジックが一致しない場合は「スタンプされていない素のベースバイナリ」と
  判定する。** ExecDBはこの場合「データなしで正常起動」だったが、
  **ExecSandboxはWASMモジュールがなければ何もできないため、エラーを出力して
  起動を中止する**（仕様書§6.2）。ここはExecDBと挙動が逆になる点に注意。
- 読み出しは `ReadAt` を使い、ファイル全体を読み込まない。ベースバイナリは
  10MB前後あるため。

## ExecDBから引き継がない部分

ExecDBのPoCのコード量の大半は、**ExecSandboxには不要**である。後から
「なぜExecDBにあった処理がここにないのか」と疑問に思いやすいので、理由を
明記しておく。

| ExecDBにあったもの | ExecSandboxでの扱い |
| :--- | :--- |
| 自分自身への上書き（`saveSnapshotSelf`） | 不要。実行中に内容が書き換わらない |
| `.execdb_old` への退避rename | 不要。上記に伴う回避策だったため |
| Linuxの `ETXTBSY` 対策 | 不要。実行中バイナリへ書き込まない |
| Windowsの `ERROR_SHARING_VIOLATION` 対策 | 同上 |
| 起動時の孤児退避ファイル掃除 | 不要 |

**ExecSandboxのWASM領域はビルド時に一度書かれ、以降は読むだけである。**
これがExecDBとの最大の違いであり、実装が軽くなっている理由でもある
（仕様書§6.2）。

## 書き込み（ビルダー側）

書き込みはビルダーという**別プロセス**が行う。実行中バイナリの制約とは無関係に
なる代わりに、ExecDBには存在しなかった構造が生じる。

- **ビルダー自身が6環境分のベースバイナリを内包する**（仕様書§6.3）。
  ビルダーのビルドには `//go:embed` を使い、生成物のスタンプとは別の仕組みで
  ある点に注意。**「ビルダーはembed、生成物はスタンプ」という二層構造**を
  混同しないこと。
- 出力ファイルには実行ビットを立てる（`0o755`）。ただしWindowsには実行ビットの
  概念がないため、パーミッションを検証するテストは
  `runtime.GOOS != "windows"` でガードすること（ExecDBが実際に踏んだ）。
- ベースバイナリは書き換えず、コピーに追記する。ビルダー内蔵の埋め込みデータは
  読み取り専用として扱う。

## 検証時の注意

- **スタンプのテストは、ビルド成果物そのものではなくコピーに対して行うこと。**
  ExecDBのテストで同種の事故があった（`.overwrite` がビルド成果物を壊し、
  次の `make build` まで壊れたままになる）。ExecSandboxは自己書き換えを
  しないため危険度は低いが、生成物を出力する先は必ず一時ディレクトリにする。
- スタンプ後の実行ファイルが実際に起動してWASMを実行できるところまで確認する。
  フッターが読めるだけでは不十分。
