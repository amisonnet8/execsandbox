# WASM ABIの互換性

ExecSandboxの独自価値は、`send`/`recv`/`conn_write` という少数のホスト関数に
集約されている（仕様書§5.1、§5.6）。この境界は**一度SDKを配布したら
壊せない**。ゲスト側のバイナリは利用者の手元でビルドされ、ExecSandbox本体の
バージョンとは独立に配布・運用されうるためである。

実装中に「ここに引数を1つ足せば楽になる」という判断は容易に出てくるが、
それは互換性を壊す変更である。以下のルールを守ること。

## 不可侵とするもの

- **既存関数のシグネチャを変更しない。** 引数の追加・削除・型変更・順序変更の
  いずれも不可。
- **既存関数の戻り値の意味を変更しない。** 特に `recv` の戻り値は値域ごとに
  意味が割り当てられている（下記）。
- **`meta_ptr` が指す8バイトのレイアウトを変更しない。**
  `[kind: u32 LE][conn_id: u32 LE]`。
- **`kind` の既存の値（0〜3）に別の意味を割り当てない。**
- **インポートするモジュール名（`execsandbox`）を変更しない。**

## `recv` の戻り値の値域（予約済み）

| 値 | 意味 |
| :--- | :--- |
| `0`以上 | 成功。ペイロード長 |
| `-1` | タイムアウト |
| `-2`以下 | バッファ不足。必要サイズは `-(戻り値) - 1` |

**新しいエラー条件を追加したくなった場合、`-1` の隣（`-2`等）を使ってはならない。**
その値域はバッファ不足のサイズ表現に連続的に消費されている。値域を分割する
必要が生じた場合は、既存のエンコードを壊さない設計を検討したうえで提案すること。

## 拡張のしかた

機能追加が必要な場合は、**既存関数を変えず、新しい関数を追加する**。仕様書
§9に挙げた将来の拡張余地は、いずれもこの形で追加できるように設計されている。

| 拡張 | 追加する関数 |
| :--- | :--- |
| 接続元アドレスの取得 | `conn_peer(conn_id, ptr, cap) -> i32` |
| アウトバウンド接続 | 起動時に許可リストで固定し、番号で選ぶ形の新関数 |

ゲストが新しい関数をimportしていても、古い本体で動かせば「未定義のimport」で
インスタンス化に失敗する。逆に新しい本体で古いゲストを動かすのは問題ない
（使わない関数がホスト側に増えるだけ）。**したがって前方互換は保証せず、
後方互換のみを保証する**という整理でよい。

## `kind` の値を追加する場合

`4`以降を使う。ゲストは未知の `kind` を受け取る可能性があるため、
**SDKライブラリ側で「未知のkindは無視してループを継続する」実装にしておくこと**。
これをしておかないと、将来イベント種別が増えたときに古いゲストがpanicする。

## 設計判断を蒸し返さないこと

以下は既に検討して退けた案である（仕様書§5）。実装中に思いついても、
新しい根拠がない限り再提案しない。

- ホストがゲストのアロケータを呼ぶ方式（言語ごとの実装差が大きい）
- メタデータをペイロード先頭のヘッダに前置する方式（責務境界を壊す）
- メタデータをi64の戻り値にパックする方式（ビット幅が足りない）
- 2フェーズ方式（サイズ取得と本体読み出しを分ける。次点ではあった）
- `send` に成功/失敗ステータスを返す（Push型でなくなる）
- `recv` のノンブロッキング専用機構（`timeout_ms = 0` で足りる）

## SDKライブラリとの関係

ABIは低レベルの契約であり、SDKライブラリはその上に言語ネイティブな皮を被せる
（仕様書§2.1）。**使い勝手の改善はSDK側で行い、ABIには持ち込まない。**
たとえば「バッファ確保を利用者から隠す」「`kind` を列挙型にする」「タイムアウトを
`time.Duration` で受ける」といったことはすべてSDKの仕事である。

ABIを変えたくなったときは、まず「SDK側で解決できないか」を検討すること。

## ABI定義の正は本リポジトリにある

SDKライブラリは別リポジトリ（`execsandbox-sdk`）にあるが、**ABIの定義を持つのは
本リポジトリの仕様書§5である。**

- SDK側にABIの定義をコピーしない。参照するだけとする。
- ABIを変更・拡張する場合、**先に本リポジトリの仕様書を更新する**。SDK側の実装が
  先行してはならない。
- 変更は必ず後方互換（上記）を保つため、SDKが古いままでも壊れない。2リポジトリ間で
  版がズレても実害が出ないのは、この保証があるためである。

依存の向きの詳細は `.claude/rules/directory-structure.md` を参照。
