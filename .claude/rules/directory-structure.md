# ディレクトリ構成

ExecSandboxは成果物が3つある（仕様書§2.1）が、そのうち**SDKライブラリは別リポジトリ
（`execsandbox-sdk`）で管理する**（後述）。本リポジトリが持つのは**本体とビルダー**の
2系統である。新しいファイルを追加する際は、必ずどちらに属するかを意識すること。

VS Codeで開発する場合、2リポジトリを並べたワークスペースにしてよい。ただし
必要なツールチェーンが異なる（本体はGo＋TinyGo、SDK側は各言語）ため、
**devcontainerには各リポジトリを個別のウィンドウで開いて入ること。** Claude Code
も同様にリポジトリごとに起動する（`CLAUDE.md`と`.claude/`はリポジトリルートから
探されるため）。

```
workspace/                      ← Git管理しない、ただの入れ物
├── execsandbox/                ← 本リポジトリ
└── execsandbox-sdk/            ← SDKリポジトリ
```

本リポジトリの構成：

```
execsandbox/
├── CLAUDE.md                   ← プロジェクトルール（参照先の案内）
├── PLAN.md                     ← 実装計画・進捗管理
├── Makefile
├── LICENSE                     （MIT）
├── go.mod
├── go.sum
├── .gitignore
├── .gitattributes              （`* text=auto eol=lf`）
├── README.md                   ← クイックスタート
├── docs/                       ← 利用者向けドキュメント
│   ├── spec/                     ← 仕様書（開発者・高度な利用者向け）
│   │   └── execsandbox_spec_ja.md    （確定済み。勝手に書き換えない）
│   ├── usage/                    ← コマンド・オプションのリファレンス
│   ├── examples/                 ← 実例集
│   └── tour/                     ← 入門ガイド（未作成。全フェーズ完了後）
├── .devcontainer/
├── .claude/
│   ├── settings.json
│   └── rules/
├── sandbox/                    ← 【ライブラリ本体】ポリシー適用とメッセージ配送
├── cmd/
│   ├── execsandbox/            ← 【本体】ベースバイナリになる実行ファイル
│   └── execsandbox-build/      ← 【ビルダー】.wasmを実行ファイルに埋め込む
├── testdata/
│   └── modules/                ← 検証用WASMモジュールのソース
├── tests/                      ← `make test` が実行するE2E/結合テスト一式
└── .github/workflows/          ← CI定義（test.yml, release.yml 等）
```

各ディレクトリ配下の具体的なファイル構成は、実装を進めながら決めてよい。ここでは
「どこに属するか」という配置の判断基準のみを定める。

## 配置の判断基準

- **WASMモジュールの実行・ポリシー適用・メッセージ配送のロジック** → `sandbox/`
- **CLIパース・起動シーケンス・ログ出力** → `cmd/execsandbox/`
- **フッターの読み出し** → `sandbox/`（本体が起動時に使う）
- **フッターの書き込み・ベースバイナリの埋め込み** → `cmd/execsandbox-build/`
- **ゲスト側で動くコード（SDKライブラリ）** → 本リポジトリには置かない。
  `execsandbox-sdk` へ
- **ゲスト側で動くコード（テスト用の検証モジュール）** → `testdata/modules/`

## 各系統の補足

### `sandbox/`（ライブラリ本体）

ExecDBの `engine` に相当する位置づけだが、**`net` への依存を禁じるという原則は
持たない**。ExecSandboxはサンドボックス間通信（AF_UNIX）と外部接続を
`sandbox` の責務として持つため、ネットワークI/Fを分離する意味がない。

代わりにこちらで守るべき境界は、**WASMモジュールの中身に意味づけをしないこと**
（仕様書§3.7）。メッセージのパース、プロトコルの解釈、ルーティング判断を
`sandbox/` に持ち込まないこと。バイト列を右から左へ渡すだけに徹する。

### `cmd/execsandbox/`（本体）

これがビルダーに同梱される**ベースバイナリ**そのものになる。したがって
ここに機能を足すと、配布物のサイズが6環境分すべてで増える
（`.claude/rules/binary-size.md`）。

### `cmd/execsandbox-build/`（ビルダー）

ベースバイナリを `//go:embed` で内包する。**ビルダーのビルドには、先に
6環境分の本体をビルドしておく必要がある**という依存関係が生じるため、
`Makefile` のターゲット順序に注意すること。

### SDKライブラリは別リポジトリ（`execsandbox-sdk`）

**本リポジトリにSDKライブラリを置かない。** 全言語のSDKは
`execsandbox-sdk` リポジトリで管理する。

分離する理由：

- **本体のCI・devcontainerを軽く保てる。** 本体は「pure Go・cgo不要・依存ゼロ」
  で、CIも`ubuntu-latest`1台のクロスコンパイルで完結する。ここにRustや
  AssemblyScript等のツールチェーンが乗ると、本体のビルド・テストが重くなり、
  `.claude/rules/binary-size.md` の方針とも噛み合わない。
- **パッケージマネージャの流儀が衝突する。** crates.io等へGoリポジトリの
  サブディレクトリから publish するのは筋が悪い。言語が増えるほどリポジトリ
  直下の作法がぶつかる。
- ExecDBが多言語ドライバ検証を別リポジトリへ分離したのと同じ構図。

#### 依存の向き

**依存は SDK → 本体の一方向であり、逆はない。**

| 依存の種類 | 内容 |
| :--- | :--- |
| 仕様への依存 | SDKはABI仕様（仕様書§5）に従う。仕様の正は本リポジトリ側 |
| **コード上の依存** | **ゼロ。** SDKは`//go:wasmimport`や`extern "C"`を宣言するだけで、本体のパッケージをimportしない |
| 成果物への依存 | SDKのテストでビルダーが要る。Releasesから取得する（CI設定のみの話） |

コード上の依存がゼロなのは、「ホストとゲストは線形メモリ越しの数値のやり取りしか
しない」というABIの性質による。この疎結合があるからリポジトリを分割できる。

#### `docs/spec/sdk_binding_ja.md` は削除済み（旧・暫定文書）

ABIがSDKからどうラップされるかの設計を暫定的に `docs/spec/sdk_binding_ja.md`
に置いていた時期があったが、`execsandbox-sdk` の立ち上げ（TinyGo版・Rust版とも
実装完了）に伴い削除した。

**移設はしなかった。** 当初の計画は「SDKリポジトリへ移設」だったが、実装が
進んだ結果 `execsandbox-sdk` 側の各パッケージREADME（`go/execsandbox/
README.md`・`rust/execsandbox/README.md`）が実測ベースのAPI説明を備えており、
暫定文書の内容と実装後のシグネチャには差分もあったため、そちらを正とすれば
移設先として重複・古い内容を持ち込むだけだと判断した（2026-09-08、ユーザー
承認済み）。同種の暫定文書を今後置く場合も、**立ち上げ後に読者が実際に読む
ドキュメントで代替できるなら、移設よりも削除を優先する**という前例になる。

#### 逆向きの依存を作らないこと

**本体は`execsandbox-sdk`の存在を知らない状態を保つ。** 本体のテストがSDKに
依存すると循環が生まれる（SDKは本体のABIに従い、本体のテストはSDKを使う）。

具体的には、`testdata/modules/` の検証用WASMはSDKを使わず**生のABIを直接叩く**
（下記）。

### `testdata/modules/`

E2Eで使う検証用WASMモジュールのソースを置く。

**SDKライブラリを使わず、`//go:wasmimport` を直書きして生のABIを叩くこと。**
これにより本体のテストが「ABIそのもの」を検証していることになり、SDKのラッパーに
バグがあっても切り分けられる。上記の逆向き依存を作らないためでもある。

ソースは手書きWAT、コンパイル済み`.wasm`はソースと共にコミットする（フェーズ①
Step 1で決定。`.claude/rules/testing.md`「現時点のツールチェーン方針」参照）。
`.wat`を編集したら `make testdata` で再生成すること。

### `tests/`

CIが自動実行する検証専用。**複数プロセスを起動して疎通を確認する**という
性質上、ExecDBのE2Eより複雑になる。プロセスの後始末には特に注意すること
（`.claude/rules/testing.md`）。

## その他

- **go.sum** はリポジトリにコミットする。Goの標準的な慣習。
- **.gitattributes** は最初から置く。ExecDBはWindowsランナーで
  `gofmt -l` が全ファイルを誤検知する問題を踏んでから追加した。
- **配布物（ビルド済みバイナリ）はリポジトリにコミットしない**
  （`.claude/rules/distribution.md`）。

## `docs/` — 利用者向けドキュメント

対象読者と目的の異なる4系統に分ける。ExecDBが実装完了後に整備した構成を、
ExecSandboxでは最初から枠として採用する。

| ディレクトリ | 対象読者 | 内容 | 状態 |
| :--- | :--- | :--- | :--- |
| `docs/spec/` | 開発者・高度な利用者 | 仕様書。各項目の判断理由と退けた案まで含む散文。SDKバインディングの暫定設計も同居 | 作成済み |
| `docs/usage/` | 全利用者 | コマンド・オプションのリファレンス。テーブル中心の索引 | 作成済み |
| `docs/examples/` | 全利用者 | 実例集。1本ずつ自己完結したユースケース | **未作成** |
| `docs/tour/` | 初学者 | 体験型の入門ガイド。番号付きの章立て | **未作成** |

### 各系統の書き分け

同じ機能について書く場合でも、系統ごとに粒度と目的が異なる。**内容が重複する
のは正常であり、片方に寄せようとしないこと。**

- **`spec/`** — 「なぜそうなっているか」。仕様の定義に、その判断理由と検討して
  退けた案を併記する。**確定済みであり勝手に書き換えない**（`CLAUDE.md`）。
  仕様と理由を1ファイルに統合しているのは、理由だけが別ファイルにあると
  参照されないまま設計判断が蒸し返されるため。なお過去の検討経緯（どういう順で
  何を捨てたか）は記録しない。**現在の仕様を選んだ理由のみを書く。**
- **`usage/`** — 「どう書くか」。オプションの一覧、書式、既定値。読者は目的の
  項目だけを引く。通読される前提で書かない。
- **`examples/`** — 「何ができるか」。1本ずつ自己完結し、読む順序を問わない。
  人間が読んで手元で試すためのもので、**CIが実行する検証（`tests/`）とは
  役割が異なる**（`.claude/rules/testing.md`）。
- **`tour/`** — 「どう学ぶか」。前の章を前提に次へ進む。`usage/`（索引）・
  `examples/`（独立したユースケース）と違い、**読む順序が意味を持つ**。

### 未作成分の作成タイミング

- **`docs/examples/`** — フェーズ③（外部接続）が完了し、仕様の主要な機能が
  ひととおり動くようになってから。実際にコマンドを実行して、出力例を実測値で
  書けるようになってからでよい。設計から想像で書くと、後で全面的な検証が
  必要になる。
- **`docs/tour/`** — 全フェーズ完了後。実装が固まる前に作ると、章立てごと
  やり直しになる。

作成時期が来たら提案すること（勝手に作り始めない）。

### 実装との同期

**仕様を変更したら `docs/usage/` も追随させること。** `docs/spec/` だけ直して
`docs/usage/` が古いまま、という状態を作らない。両者は同じ内容を異なる粒度で
書いたものであり、片方だけが正しい状態は許容しない。

`docs/usage/` は実装前に仕様から起こしたものであり、**コマンドの出力例は
未検証**。実装が進んで実際に動かせるようになったら、実測値へ差し替えること。

### README の扱い

各 `docs/` サブディレクトリと、リポジトリ直下の `README.md` は現時点で未作成。
`README.md` は、インストールと最初の一歩に絞ったクイックスタートに徹し、詳細は
`docs/` 配下へリンクする方針とする。**動作するリリースが出る前に書いても
書き直しになる**ため、フェーズ④のリリース準備と合わせて作成する。
