# テスト方針

## 開発環境の前提

開発者の手元環境は**Linuxのみ**。Windows/macOSでの実際の動作確認は、手元では
行わず GitHub Actions（`windows-latest`/`macos-latest` 等のホステッドランナー）
に委ねる。パブリックリポジトリ（MITライセンス）のため、GitHub Actionsは実質
無制限に利用できる。

| 対象 | 進め方 |
| :--- | :--- |
| コアロジック（`sandbox`パッケージ、フッター読み書き、メールボックス、フレーミング） | まずLinux環境・Goのみで開発し、ロジックの正しさを固める。フィードバックループを最速に保つ。 |
| **AF_UNIXのクロスプラットフォーム動作** | **最優先で早期に確認する。** 仕様書§3.1でWindowsを含む全プラットフォームをAF_UNIXに統一すると決めており、これが崩れると設計判断（名前付きパイプへの分岐が必要か）まで戻る。フェーズ①Step 5で必ず確認すること。 |
| スタンプ方式のクロスプラットフォーム動作 | 実行ビットの扱いがOSで異なる。下記「落とし穴」参照。 |
| ゲスト側（WASMモジュール） | TinyGoでビルドした検証用モジュールを使う。手元Linuxで完結する。 |
| 依存ライブラリの脆弱性・ライセンスチェック | GitHub Actions上で `trivy` を実行し、既知の脆弱性（CVE）とライセンス互換性（MIT/BSD/Apache-2.0等は許可、GPL系等は拒否）をチェックする。ソースコード自体のコピペ検出は対象外（人間レビューに委ねる）。 |

## 実装後の動作確認について

実装したら、必ずビルド確認に加えて実際の動作確認を行うこと。ロジック上正しそうに
見えても、実際に動かして初めて見つかる不具合は起こりうる。

- `make test`（E2E）を走らせる粒度は、作業規模に応じて判断する。
  - 小規模な修正（数行、1関数内で完結）は、一連の作業が終わった最後に1回でよい。
  - 大規模な変更（複数ファイルにまたがる、設計に関わる）は、各ステップの区切り
    ごとに実行すること。
  - **判断に迷ったら、実行する側に倒すこと。**

## 検証用WASMモジュール

ExecSandboxのテストには、**ゲスト側のコードが必要**という、ExecDBにはなかった
性質がある。

### 現時点のツールチェーン方針

**devcontainerにはTinyGoを入れていない。** `wabt`（`wat2wasm`）のみを入れている。

- フェーズ①Step 1のスパイク検証は、手書きのWATから`wat2wasm`でモジュールを作る
  ほうが**ABIの検証として純粋**である。TinyGoのコード生成の癖が混入しない。
- **検証用モジュールは、ビルド済み`.wasm`を`.wat`ソースと併せてコミットする**
  （Step 1で決定）。CI（Windows/macOSランナー含む）に`wat2wasm`の導入を前提にせず
  済む。`.wat`を編集したら `make testdata` でローカルの`wat2wasm`を使って
  `.wasm`を再生成し、両方をコミットすること。前者ならTinyGoは不要。
- `wabt`はaptで確実に入るが、TinyGoは公式のdevcontainer featureが存在するか未確認
  であり、GitHub Releasesからの取得はバージョンとアーキテクチャの直書きになる。

**TinyGoが必要と確定した時点で追加すること。** その際は、
`.devcontainer/postCreate.sh` に切り出して `dpkg --print-architecture` で
amd64/arm64を分岐させること（`amd64`直書きはarm64マシンで壊れる）。

### モジュールの書き方

- `testdata/modules/` にソースを置き、テストで使う。
- **SDKライブラリを使わず、生のABIを直接叩くこと。** 手書きのWAT、または
  TinyGoの`//go:wasmimport`直書きのいずれか。SDKは別リポジトリ
  （`execsandbox-sdk`）にあり、本体がそれに依存すると循環が生まれる（SDKは本体の
  ABIに従い、本体のテストはSDKを使う、という関係）。生のABIを叩けば、テストが
  検証しているのが「ABIそのもの」であることが明確になり、SDKのラッパーにバグが
  あっても切り分けられる。
- 目的別に小さく分けること。「受け取ったものをそのまま送り返す」「一定回数
  送ったら終了する」「大きいメッセージを送る」など、1モジュール1目的。
- **ゲスト側の異常系も用意すること。** ABIを誤用するモジュール（範囲外の
  ポインタを渡す、バッファ長を偽る等）に対して、ホストが安全に振る舞うことを
  確認する。サンドボックスである以上、ゲストは信頼できない前提で書く。
  SDKを経由しないからこそ、こうした誤用を意図的に書ける。
- ビルド済み `.wasm` は `.wat` ソースと共にコミットする（フェーズ①Step 1で
  決定。「現時点のツールチェーン方針」参照）。`.wat`編集後は`make testdata`で
  再生成すること。

なお**言語をまたぐ相互接続の検証**（TinyGo製とRust製のサンドボックスを繋ぐ等）は
`execsandbox-sdk` 側の責務であり、本リポジトリでは行わない。

## 複数プロセスを扱うE2Eの注意

ExecSandboxのE2Eは、**複数のサンドボックスを起動して疎通を確認する**という
性質上、ExecDBのE2Eより複雑になる。ExecDBが実際に踏んだ落とし穴のうち、
ここでも該当するものを先回りして記しておく。

- **起動したPIDは配列に記録し、`trap ... EXIT` で無条件にkillする安全網を
  必ず用意する。** 個別の停止処理とは別に用意すること。テストが途中で失敗した
  とき、孤児プロセスが残ると次回以降の実行が壊れる。
- **孤児プロセスはサイレントに次回のテストを偽装する。** ExecSandboxの場合、
  残ったソケットファイルを掴んだままのプロセスがいると、新しく起動したはずの
  サンドボックスではなく古い方に接続してしまう可能性がある。テストが原因不明に
  失敗する場合は、まず `ps` とソケットファイルの残骸を確認すること。
- **ソケットファイルは一時ディレクトリ配下に作らせること。** テスト実行時の
  カレントディレクトリのまま起動すると、リポジトリ直下にゴミが残る。
  `XDG_RUNTIME_DIR` を一時ディレクトリに向けるのが確実
  （仕様書§3.2のパス解決がこの環境変数を見るため）。
- **`set -e` 下でのコマンド置換への代入は、内部コマンドが非ゼロで終了すると
  スクリプトごと落ちる。** エラーを検証したいテストでは `|| true` で明示的に
  握りつぶす。
- **パイプの各段は別サブシェルで実行され、`set -e` が継承される。** 終了コードを
  ファイル経由で受け取る場合は、そのサブシェルの先頭で `set +e` すること。
- **裸の `exec` にリダイレクトを付けると、シェル全体に恒久的に適用される。**
  単一コマンドのつもりでも `{ ... } 2>/dev/null` のようにグループ化すること。

## クロスプラットフォームCIの落とし穴

ExecDBがCI上でのみ顕在化した問題を踏んでいる。手元Linuxでは再現しない種類の
ものなので、先回りして記しておく。

- **`Makefile` やシェルスクリプトで `/dev/stderr` 等のUnix固有パスに依存しない。**
  Windowsランナー（Git Bash/MSYS）で壊れる。出力を変数に受けて `echo "$var" 1>&2`
  で書くこと。
- **`.gitattributes`（`* text=auto eol=lf`）を最初から置く。** これがないと
  Windowsランナーで `.go` がCRLFで展開され、`gofmt -l` が全ファイルを未整形と
  誤検知する。
- **GitHub Actionsの `uses: owner/repo@TAG` は実際のタグ名と厳密に一致させる。**
  特に `v` プレフィックスの有無を見落としやすい。
- **Windowsには実行ビットの概念がない。** `os.Chmod(path, 0o755)` 後に
  パーミッションを検証するテストは失敗する。`runtime.GOOS != "windows"` で
  そのアサーションだけガードすること。**ビルダーの出力に実行ビットを立てる
  実装をテストする際、必ず該当する。**

## `-race` の運用方針

ExecSandboxはホスト側でメールボックス・複数の接続・タイムアウトを扱うため、
並行性のバグは `-race` で継続的に検出したい。一方 `-race` はcgoを要求するため、
「本体はpure Go・`CGO_ENABLED=0`」という方針とは別枠で扱う。

- **`make race`（`CGO_ENABLED=1 go test -race -count=1 ./...`）を新設し、
  `make check` には含めない。** `check` はコミット前に素早く回す用途なので、
  cgoビルド分の速度低下・追加の外部依存を持ち込まない。
- GitHub Actionsでは `race` を別ジョブにし、`ubuntu-latest`/`macos-latest`
  限定で実行する。**`windows-latest` にはCコンパイラが標準で入っていない**ため
  対象から外す。
