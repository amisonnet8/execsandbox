# ExecSandbox 仕様書

**版**：v1 draft

WASM実行ランタイムとWASMモジュールを単一の実行ファイルに内包する、サンドボックス
実行ツールの仕様。

各項目には、その仕様を選んだ判断理由を併記する。実装中に別案を思いついた場合は、
まず該当箇所の理由と「検討して退けた案」を確認すること。

コマンド・オプションの実務的なリファレンスは `../usage/` を参照。

---

## 1. 用語

| 用語 | 定義 |
|---|---|
| **ExecSandbox** | WASMモジュールを内包した実行ファイル、およびそのプロセス |
| **WASMモジュール** | サンドボックス内で実行されるWASMバイナリ |
| **ホスト** | ExecSandboxのGo側実装。WASMモジュールの外側 |
| **ゲスト** | WASMモジュール側 |
| **メールボックス** | 受信側が持つ、届いたメッセージの待ち行列 |
| **宛先** | `send`の送信先。起動時に番号へ割り当てる |
| **ID** | ExecSandboxインスタンスの論理名。ソケットパスに解決される |
| **connID** | 外部接続1本に割り当てられる識別番号 |
| **ビルダー** | `.wasm`を実行ファイルに変換するコマンド（`execsandbox-build`） |

用語はコード・コメント・ログでも一貫して使う。特に以下は混同しやすい。

| 使う語 | 使わない語 |
|---|---|
| メールボックス | キュー、チャネル、バッファ |
| 宛先 | 送信先、ターゲット |
| ホスト / ゲスト | サーバー / クライアント |
| 外部接続 | TCP（Unixドメインソケットの場合もあるため） |

## 2. 構成

### 2.1 構成要素

| 要素 | 実装 | 内容 |
|---|---|---|
| ExecSandbox本体 | Go | `sandbox`（ポリシー適用とメッセージ配送）＋`cmd/execsandbox`（CLI）。`wazero`を組み込む |
| WASMモジュール | 言語非依存 | WASMバイナリとして妥当であれば言語を問わない |
| SDKライブラリ | 言語別 | 5章のABIをラップする。言語ごとに1本。**別リポジトリ**（`execsandbox-sdk`） |
| ビルダー | Go | `.wasm`を実行ファイルに埋め込む。言語非依存で1つ |

`wazero`を採用するのは、CGO不要・依存ゼロのPure-Go WASMランタイムであり、
「単一バイナリ・cgo不要」という配布形態をそのまま実現できるため。

**配布は言語ごとの開発キット（SDKライブラリ＋ビルダー）という単位で行い、
ビルダーは全キットで共通のものを同梱する。**

構成要素としてはSDKライブラリ（言語別）とビルダー（言語非依存）は別物である。
ビルダーの入力は`.wasm`バイナリであり、それがどの言語から出たかを区別しないため、
1つあれば足りる。一方、サンドボックスを作る側から見れば両者はセットで初めて意味を
持つ。「WASMモジュールを書く」だけでは成果物にならず、「実行ファイルにする」までが
一連の作業だからである。

この形により、新しい言語へ対応するコストはライブラリを1本書くだけになる。ビルダーは
スタンプ方式（6.2）によりGoツールチェーンを要求しない単一バイナリであるため、たとえば
Rust開発者にGoのインストールを強いることなく同梱できる。

#### SDKライブラリを別リポジトリとする理由

本体・ビルダーとSDKライブラリはリポジトリを分ける。

- 本体は「pure Go・cgo不要・依存ゼロ」であり、CIも1台のクロスコンパイルで完結する。
  ここに各言語のツールチェーンが乗ると本体のビルド・テストが重くなる。
- パッケージマネージャの流儀が言語ごとに異なり、1つのリポジトリ直下では衝突する。

**依存はSDK→本体の一方向であり、コード上の依存はゼロである。** SDKはホスト関数の
importを宣言するだけで、本体のパッケージを参照しない。「ホストとゲストは線形メモリ
越しの数値のやり取りしかしない」というABIの性質が、そのまま疎結合になっている。

ABIの定義を持つのは本仕様書§5であり、SDK側はこれを参照する。ABIは後方互換のみを
保証する（§5.1）ため、2リポジトリ間で版がズレても既存のモジュールは壊れない。

### 2.2 実行モデル

- ExecSandboxは1プロセスにつき1つのWASMモジュールを実行する。
- 複数のExecSandboxプロセスを起動時オプションで相互に配線することで、システムを
  構成する。
- 役割（コア、中継、ブローカー、外部I/F、管理等）による機構上の区別は設けない。
  すべて同一の仕組みで動作する。
- 複数プロセスの起動・停止・監視は本ツールの責務外とする。

#### 役割を機構で区別しない理由

「処理を行うもの」「中継するだけのもの」「束ねるもの」といった区別をプリミティブの
レベルで設けない。どの役割も構造的には同じ1つのExecSandboxインスタンスとして実現
される。

これにより「システムを構築する」という行為は、役割の異なるインスタンスを起動時の
宛先指定で繋ぎ合わせるグラフを作ることに集約される。特別な中継用プリミティブを
持ち込まず、組み合わせだけでシステムが組み上がる一貫性を重視した。

トポロジー（P2Pメッシュ、ハブ&スポーク、混在）は構成者が自由に選び取れる。仲介役を
挟む構成は宛先管理を集中させやすくなる一方、単一障害点が生まれるトレードオフを伴う。

#### 管理用インターフェースを持たない理由

ExecSandbox自身を操作する管理用プロトコルは持たない。管理用途が必要な場合も、
管理役のExecSandboxを1つ作って組み合わせることで表現する。

管理のために本体へ特別な機構を組み込むと、上記の「どの役割でも仕組みは同一」という
一貫性が崩れ、最小限に絞ったはずのホストの責務（3.7）も膨らむ。管理もまた1つの役割に
過ぎない、と位置づけることでこれを避けている。

#### プロセス管理を持たない理由

各サンドボックスは独立したプロセスとして起動時オプションで配線されるだけなので、
まとめて起動する手段はシェルスクリプトで足りる。

```sh
#!/bin/sh
./dbcore -n dbcore -v /data:/data &
./extif  -d 1=dbcore -l 5432 &
./repl   -d 1=dbcore -s in,out
```

専用の起動機構を作ればDocker Composeやsupervisordの再発明になり、本体に管理用の
概念を持ち込むことになる。既存の仕組みに委ねる。

## 3. サンドボックス間通信

### 3.1 通信路

- サンドボックス間通信にはUnixドメインソケット（AF_UNIX）を用いる。全プラット
  フォーム共通とする。
- 通信範囲は同一ホスト上のプロセス間に限る。

#### AF_UNIXを選んだ理由

通信範囲を同一ホスト上に限定しているため、ネットワークスタックを経由しないUnix
ドメインソケットが最も素直である。加えて、**ソケットファイルのパーミッションに
よってOSレベルのアクセス制御が得られる**点が、ケイパビリティベースという設計思想
（3.3）と噛み合う。

WindowsもWindows 10 (1803)以降でAF_UNIXをネイティブサポートしており、Goの
`net.Listen("unix", path)`がそのまま動作する。以下は不採用とした。

- **Windowsのみ名前付きパイプ**：Windowsで最も一般的なプロセス間通信だが、Go標準
  ライブラリに実装がなく`go-winio`等の外部依存が必要になる。「cgo不要・依存ゼロ」
  というスタイルが崩れる。
- **Windowsのみループバック TCP**：標準ライブラリだけで書けるが、ポート番号の管理が
  必要になるうえ、ファイルパーミッションによるアクセス制御が失われ、ローカルの他
  ユーザーからも接続できてしまう。

単一のコードパスで済むことを優先した。

### 3.2 アドレス解決

IDからソケットパスへの解決は以下の固定パターンで行う。

| 環境 | パス |
|---|---|
| Unix系（`$XDG_RUNTIME_DIR`設定時） | `$XDG_RUNTIME_DIR/execsandbox/<ID>.sock` |
| Unix系（未設定時） | `/tmp/execsandbox-<uid>/<ID>.sock` |
| Windows | `%LOCALAPPDATA%\execsandbox\<ID>.sock` |

- `/tmp`配下にディレクトリを作成する場合、パーミッションは`0700`とする。
- 待ち受け開始時、既存のソケットファイルが存在する場合は接続を試み、応答がなければ
  削除してからbindする。

`/tmp`直下を避けるのは、他ユーザーから見える場所に置くとパーミッションによる
アクセス制御が弱まるため。`$XDG_RUNTIME_DIR`（通常`/run/user/<uid>`）は起動ユーザー
専用のディレクトリであり、この点で望ましい。

ソケットパスを直接指定させずID（論理名）を介するのは、パスの実装詳細を利用者から
隠すため。

### 3.3 宛先とケイパビリティ

- 自身のIDは起動オプション`-n`で指定する。指定しない場合、サンドボックス間
  メッセージを受信しない。
- 宛先は起動オプション`-d N=ID`で番号に割り当てる。番号は1以上の整数。
- ゲストは番号のみを指定して送信する。宛先の実体を知る手段を持たない。
- 起動時に割り当てられていない宛先へは送信できない。

#### 起動時指定が安全境界を担う

宛先の起動時指定は、単なる利便性のための設定ではなくサンドボックスとしての
**安全境界**である。

- **起動時指定**：「このWASMモジュールがどの相手と通信してよいか」を、起動する側
  （信頼できる人間・システム）があらかじめ決める許可リスト。ゲストが実行時に任意の
  宛先へ自由に接続できてしまうと、サンドボックスの隔離が意味をなさない。
- **実行時の`send`**：許可された宛先の中から「今回はどれに送るか」をゲストが選択
  するだけであり、許可されていない相手には物理的に送信できない。

**この「隔離を決めるのは起動する側である」という原則は例外を持たない。** ビルド時に
ポリシーを焼き込むこともしない（6.1）。

#### 宛先を番号で指す理由

サンドボックス名や役割名のような文字列識別子ではなく、Unixのファイルディスクリプタ
0/1/2のような番号を採る。

```
起動時: 宛先1=nodeB, 宛先2=nodeC, 宛先3=logger
ゲスト: send(1, data)   // "宛先1"に送る、としか書かない
```

ゲストは番号にしか触れないため宛先の実体を知らずに済み、起動時の配線を変えるだけで
同じWASMモジュールを別のシステム構成に転用できる。

### 3.4 送信の挙動

`send`は以下の場合いずれもエラーを返さず、メッセージを破棄する。

| 条件 | ホスト側ログ |
|---|---|
| 宛先番号が未割り当て | 出力しない |
| 宛先が未起動、または接続不可 | 出力しない |
| 送信データ長が`--max-frame`を超える | 出力する |
| 相手のメールボックスが上限に達している | 受信側が出力する（3.6） |

宛先への接続は初回送信時に確立する。失敗した場合は次回送信時に再試行する。

#### 未設定宛先を黙って捨てる理由

Unixの`/dev/null`と同じ扱いとする。許可されていない宛先への送信は届かないだけで、
システム全体を止めない。

tail-drop（3.6、ログを出す）と扱いが異なるのは、両者の性質が違うためである。未設定の
宛先は起動オプションを見れば分かる**静的な状態**であり通知を要しない。一方tail-dropは
実行中の負荷に依存する**動的な現象**で、記録しなければ外から観測できない。

#### 遅延接続にする理由

各サンドボックスをシェルスクリプトでまとめて起動できるようにするには、「宛先がまだ
起動していない状態」が許容される必要がある。そのため接続は初回送信時に確立し、失敗
しても次回再試行する形とした。

相手が起動するまでの間に送信されたメッセージは黙って捨てられるが、これは起動直後に
限られる一過性の状態である。

### 3.5 フレーミング

サンドボックス間メッセージは以下の形式で転送する。

```
[長さ: u32 リトルエンディアン][データ本体]
```

- 受信側は宣言された長さぶんを読み切ることで1通の境界を確定する。
- 長さが`--max-frame`を超えるフレームは受理せず破棄する。
- ゲストはこの形式を意識しない。ホストが付与・解釈する。

#### 長さプレフィックスを採る理由

区切り文字方式（改行やNULバイト等）は、送信データに同じバイトが含まれると壊れ、
エスケープ処理が必要になる。長さプレフィックスであれば中身との衝突が原理的に起こらず、
「送ったバイト列がそのまま届く」ことを無条件に保証できる。

リトルエンディアンとしたのは、WASMの線形メモリ表現に合わせてゲスト側の変換を不要に
するため。u32の幅をそのまま上限とすると巨大な長さを宣言してホストにメモリを確保
させられるため、`--max-frame`で別途上限を設けている。

### 3.6 メールボックス

- メールボックスは受信側プロセスが保持する。
- 上限は通数で指定する（`-b, --mailbox-limit`）。
- 上限に達した状態で新たなメッセージが到着した場合、**そのメッセージを破棄する**
  （tail-drop）。既存のメッセージは破棄しない。
- 破棄をゲストに通知しない。
- 破棄はホスト側stderrに記録する。連続発生時はレート制限し、初回出力後は一定間隔で
  累計数を出力する。

#### tail-dropを選んだ理由

head-drop（古いものから捨てる）は、いったんキューに入った並びが後から崩れるため、
保証すると決めた「同一送信元内の順序」（3.7）と矛盾する。

上限の単位を通数としたのは、`--max-frame`と組み合わせることで通数×最大フレーム長と
してメモリ上界が定まるため。

### 3.7 保証範囲

ホストが保証するのは以下の2点のみ。

1. **フレーム境界**：送信されたバイト列が、そのまま1通として受信側に渡ること。
2. **同一送信元内の順序**：ある送信元が送った複数のメッセージが、その送信元内での
   送信順で並ぶこと。

以下は保証しない。

- 宛先への到達
- 異なる送信元同士の順序関係
- メッセージ内容の解釈・検証・ルーティング

#### 到達保証を外した理由

Push型（送信側が相手の受け取り可否を問い合わせず、応答も待たない）を貫いた帰結で
ある。受信側が詰まればメッセージは破棄されるため、「必ず届く」とは言えない。

到達確認が必要なシステムはゲスト側でACKを設計する。これは「配送の都合だけをホストが
持ち、意味づけはゲストに委ねる」という境界と一貫する。

#### fan-out / fan-in が仕組みなしに得られる

- **fan-out**：起動時に宛先を複数指定できるという設計だけで実現される。中継役を別途
  用意する必要がない。
- **fan-in**：受信側は送信元を区別せず同じメールボックスに溜めるため、複数の送信元
  から届けること自体が最初から可能。

この性質があるため、`send`に一斉配布用の形態を追加する必要がない。SDK側のループ
ヘルパーで足りる。加えて、複数宛先のうち一部だけが詰まっている場合の振る舞いという
曖昧さを生まずに済む。

## 4. 外部接続

### 4.1 待ち受け

- 起動オプション`-l, --listen`で待ち受けアドレスを指定する。省略時は待ち受けを
  行わない。
- **1インスタンスにつき1つのみ指定できる。**
- 実際のソケット操作（listen、accept、コネクション管理）はホストが行う。

#### ホストがソケットを持つ理由

`wazero`のネットワーク対応は、WASI Preview 1の`sock_accept`等が限定的、
`experimental/sys`のアウトバウンドTCP許可リストも実験段階で未成熟なため、これらに
頼らず独自のホスト関数を新設する方針を採る。

実際のソケットは`net.Listen`等の枯れた標準ライブラリで扱い、安全性・成熟度をGo側に
閉じ込める。ゲストにはコネクション単位のバイトストリーム読み書きだけを渡し、
プロトコルの中身の解釈はすべてゲストのロジックとする。

#### 待ち受けを1つに限る理由

複数のリスナーを許すと、connIDだけでは「どのリスナー経由の接続か」が判別できず、
イベントにリスナー番号を追加する必要が生じる。複数必要な場合は外部I/F役の
ExecSandboxを複数立て、コア役へ向ける構成で表現できる。

#### 待ち受けアドレスの既定をループバックにする理由

書式はnginxの`listen`ディレクティブに倣いつつ、ポート番号のみを指定した場合の既定は
逆にした（nginxは全インターフェース）。ExecSandboxはWebサーバーではなくサンドボックス
であり、**最も短い書き方が最も安全な設定であるべき**と考えたため。PostgreSQLの
`listen_addresses`やRedisの`bind`が既定をループバックとしているのと同じ方針である。

### 4.2 接続の識別

- ホストは接続ごとにconnIDを割り当てる。
- connIDは単調増加するu32とし、切断後も再利用しない。u32が一巡した場合、生存中の
  connIDは飛ばして割り当てる。
- ゲストはconnIDのみを扱い、接続の実体を知る手段を持たない。

切断イベントは必ず配送されるため、ゲストが切断時に状態を破棄していれば取り違えは
起きない。再利用しない設計にしておけば、破棄し忘れた場合も別の接続と混同することが
なく、ゲスト側のバグとして切り分けられる。

### 4.3 データの流れ

- **受信方向**：接続の確立・データ到着・切断は、いずれもメールボックスへイベントと
  して流入する（5.3参照）。専用の受信関数は設けない。
- **送信方向**：`conn_write`で書き戻す。

外部接続由来のデータについて、ホストは接続内での順序のみを保証する。チャンクの区切り
位置に意味はなく、3.5のフレーミングは適用されない。

#### 受信をメールボックスに合流させる理由

素朴に`accept()`のようなブロッキング関数を置くと、外部接続と`recv()`という2つの待ち口
が生じる。シングルスレッドでブロッキング関数しかない以上、片方で待っている間はもう
片方に反応できず、`recv()`で待っている最中に新しい接続を取りこぼすデッドロックになる。

受信イベントをメールボックスに流し込めば待ち口が1つに統一され、この問題が消える。
Erlangがポート（外部プロセスやソケット）からの入力を通常のメッセージと同じメール
ボックスに配送するのと同じ形であり、アクターモデルの筋にも合う。

合流させたのは受信方向のみ。送信方向は待ち口の問題と無関係なため`conn_write`として
残した。結果として独自ホスト関数として増えるのは`conn_write`ひとつで済んでいる。

#### 標準入出力を合流させない理由

同じ理屈でstdioも寄せるべきかという論点があるが、外部接続とは非対称に扱う。

- 外部接続は**どうせ独自実装が必要**だったため、合流の追加コストがゼロで、待ち口が
  減る分だけ得になる。一方stdioは**WASI標準でそのまま手に入っており**、合流させた
  瞬間にその標準機構を捨てることになる。
- 捨てるものが大きい。TinyGoの`fmt.Println`、Rustの`println!`、Cの`printf`が動かなく
  なり、SDKが独自の出力関数を提供せざるを得ない。ゲスト側ランタイムのpanicメッセージは
  stderrに出るため、潰すとサンドボックスが落ちた理由が見えなくなる。シェルのリダイ
  レクトも失われる。
- **型が合わない。** メールボックスは1通の境界を保証する仕組みだが、stdioは境界を
  持たないバイトストリームである。行区切りにすれば、否定したはずの区切り文字方式が
  裏口から復活する。

したがって統一原理は「すべてをメッセージにする」ではなく、**「どうせ独自実装が要る
ものだけメールボックスに寄せる」**と置く。

なお待ち口の競合は、逐次的なやり取りしかしないサンドボックス（REPL等）では発生
しない。人間の入力と非同期な割り込みを同時に待つ構成が必要になった場合は、起動時
オプションで「stdinをメールボックスに流す」配線を選べるようにする形で後付けできる。

### 4.4 制限

- ゲストから外部へ接続を開始する手段（アウトバウンド）は提供しない。
- 接続元IPによるフィルタリングは行わない。
- 接続元アドレスをゲストに渡さない。

#### アウトバウンドを持たない理由

制限しているのは通信の向きではなく、**どちらが接続を開始するか**である。

```
外部 → ExecSandbox   接続を開く：可
外部 ← ExecSandbox   応答を返す：可（既存接続への書き戻し）
外部 ← ExecSandbox   接続を開く：不可
```

アウトバウンドを許すと、ゲストが自分で行き先を選べてしまう。宛先を起動時の許可
リストに固定した意味（3.3）が失われ、マウントしたファイルを任意の外部へ送出できる。
一方インバウンドは接続を開くのが外部の側なので、ゲストが行き先を選ぶ問題自体が
起きない。

#### 接続元フィルタを持たない理由

PostgreSQLの`pg_hba.conf`のような接続元許可リストは認証と一体の機構である。認証を
持たず、プロトコルの中身にも関知しないExecSandboxが単独で持つ理由が薄い。ファイア
ウォールやリバースプロキシに委ねる。

## 5. WASM ABI

### 5.1 インポート

モジュール名は`execsandbox`。

| 関数 | シグネチャ |
|---|---|
| `send` | `(dest: i32, ptr: i32, len: i32)` |
| `recv` | `(meta_ptr: i32, buf_ptr: i32, buf_cap: i32, timeout_ms: i32) -> i32` |
| `conn_write` | `(conn_id: i32, ptr: i32, len: i32) -> i32` |
| `max_frame` | `() -> i32` |

バッファはゲストが確保する。ホストはゲストのメモリへ書き込むのみで、ゲストの
アロケータを呼び出さない。

#### バッファをゲスト持ちにする理由

ホストがゲストのアロケータをexport経由で呼び出す方式（wasm-bindgen等が採る形）は、
アロケータのexport方法がTinyGo/Rust/C/AssemblyScriptで大きく異なり、「新しい言語への
対応はライブラリを1本書くだけ」という狙い（2.1）に最も重いコストをかける。ホストから
ゲストへの再入が発生しない点でも、ゲスト持ちのほうが単純である。

#### ABIは互換性を壊さない

一度SDKを配布したら、既存関数のシグネチャ・戻り値の意味・`meta_ptr`のレイアウト・
`kind`の既存値・モジュール名のいずれも変更しない。ゲスト側のバイナリは利用者の手元で
ビルドされ、本体のバージョンとは独立に配布・運用されうるためである。

拡張は新関数の追加で行う。ゲストが新しい関数をimportしていても、古い本体で動かせば
「未定義のimport」でインスタンス化に失敗する。逆に新しい本体で古いゲストを動かすのは
問題ない。したがって**前方互換は保証せず、後方互換のみを保証する**。

### 5.2 `send`

指定した宛先番号へ、線形メモリ上の`ptr`から`len`バイトを送信する。戻り値を持たない。
破棄条件は3.4を参照。

#### 戻り値を持たない理由

未設定宛先への送信も相手のメールボックス詰まりも黙って捨てると決めている以上、ゲストが
結果を知る手段があってはならない。voidとすることで、その意味論がABIの型に現れる。

成功/失敗ステータスを返す案も検討したが、相手のメールボックスに入ったかを返すには受理を
待つ必要があり、待った時点でPush型ではなく同期RPCになる。fan-outで一部の宛先だけが
詰まっている場合に全体をブロックするのか、という問題も生じる。かといって「ローカルの
送信バッファに書けたか」だけを返すのでは、相手に届いたことを何も保証せず、「成功が
返ったのに届いていない」という最も混乱する形になる。

`conn_write`だけが戻り値を持つのは非対称に見えるが、こちらはconnIDの有効性というゲストが
追跡している動的な状態に関わり、不一致は明確なバグを意味するため区別している。

### 5.3 `recv`

メールボックスから1通取り出す。

**`timeout_ms`**

| 値 | 動作 |
|---|---|
| 負値 | メッセージが到着するまで無限に待つ |
| `0` | 即座に戻る |
| 正値 | 指定ミリ秒まで待つ |

**戻り値**

| 値 | 意味 |
|---|---|
| `0`以上 | 成功。値はペイロード長。`buf_ptr`へコピー済み。メールボックスから取り除かれる |
| `-1` | タイムアウト。`meta_ptr`および`buf_ptr`は書き換えられない |
| `-2`以下 | バッファ不足。必要サイズは`-(戻り値) - 1`。コピーは行われず、メッセージはメールボックスに残る |

**メタデータ**

`meta_ptr`に8バイトを書き込む。

```
[kind: u32 リトルエンディアン][conn_id: u32 リトルエンディアン]
```

| `kind` | 種別 | `conn_id` | ペイロード |
|---|---|---|---|
| `0` | サンドボックス間メッセージ | 未使用 | あり |
| `1` | 外部接続・確立 | 有効 | なし |
| `2` | 外部接続・データ | 有効 | あり |
| `3` | 外部接続・切断 | 有効 | なし |

外部接続の3種類は、1本の接続の一生を「開始・継続・終了」に分けたもの。複数の
クライアントが同時に接続している場合、connIDごとに独立して発生し、時間軸上では入り
混じって1本のメールボックスに流れてくる。ゲストはconnIDをキーにした状態テーブルを
持ち、確立で作り、データで更新し、切断で破棄する。

「切断」イベントが必要なのは、これがないとゲストが接続ごとに保持している状態
（プロトコルのパース途中の状態等）をいつ破棄してよいか判断できず、リークするため。

#### ブロッキングとする理由

WASI Preview 1のWASMモジュールはシングルスレッドで、イベントループやコールバックを
持たない。ノンブロッキングにするとゲストはビジーウェイトを書くしかなく、常駐
サンドボックスがCPUを回し続ける。Erlangの`receive`がブロックするのと同じ理由である。

ノンブロッキングが欲しくなる主な動機は「複数の待ち口を同時に見たい」ことだが、外部
接続を合流させたこと（4.3）で待ち口が1つしかなく、`select`相当を必要とする状況が
生じない。

一方タイムアウトはビジーウェイトを生まず、これがないと以下が書けないため設けた。

- **定期的な処理**：一定時間ごとにハートビートを送る、統計を出力する等
- **タイムアウト付きのACK**：到達保証が必要ならACKを設計せよ（3.7）と促しておき
  ながら、応答が返らなかった場合に諦める手段がないと、その設計自体が完結しない

#### メタデータをペイロードと分ける理由

バイト列の先頭に固定長ヘッダ（種別＋connID）を前置する方式も検討したが、ホストが
ペイロードそのものに書き込むことになり、「メッセージの中身にホストは一切意味づけ
しない」という責務境界（3.7）に例外を作ってしまう。別枠で返せばペイロードは純粋な
まま保たれる。

メタデータをi64の戻り値にパックする案は、種別＋connID＋長さが64ビットに収まらず、
いずれかのビット幅を削る妥協を仕様に埋め込むことになるため不採用とした。

2フェーズ方式（サイズだけ受け取ってから本体を読む）は「バッファ不足」が原理的に
起きない堅実な案で次点だったが、単一呼び出しで済むならそのほうが単純なため採用
しなかった。

#### 戻り値でサイズ不足とタイムアウトを表現する理由

負数にまとめることで、別途エラーコード体系を設けずに済む。

なお`max_frame()`があるため、再確保のパスは実質的に使われない。ゲストは起動時に一度
これを呼んでバッファを確保すれば、以後どのメッセージも収まる。それでも負数の返却を
仕様に残しているのは、`--max-frame`を極端に大きく設定した構成や、ゲストが意図的に
小さいバッファで済ませたい場合の逃げ道としてである。

**新しいエラー条件を追加する場合、`-1`の隣（`-2`等）は使えない。** その値域は
バッファ不足のサイズ表現に連続的に消費されている。

#### 未知の`kind`は無視する

`kind`に`4`以降を追加する余地があるため、SDKライブラリは**未知のkindを無視してループを
継続する**実装とする。これをしておかないと、将来イベント種別が増えたときに古いゲストが
壊れる。

### 5.4 `conn_write`

`conn_id`の接続へ、線形メモリ上の`ptr`から`len`バイトを書き込む。

| 戻り値 | 意味 |
|---|---|
| `0` | 成功 |
| `-1` | 不明なconnID |

### 5.5 `max_frame`

`--max-frame`に設定された値をバイト数で返す。

### 5.6 独自実装の範囲

設計を棚卸しすると、独自の実装を必要とする領域は2つに絞られる。

| 項目 | 実装 |
|---|---|
| 引数・環境変数、ファイルシステム、メモリ上限、乱数・時刻、標準入出力 | WASI／wazero標準をそのまま利用 |
| サンドボックス間通信（`send`/`recv`） | 独自実装（WASI標準にこの概念がないため） |
| 外部接続の橋渡し（`conn_write`） | 独自実装（WASIのソケット対応が未成熟なため） |

標準機能にCLIオプションの皮を被せただけの部分は、極端に言えば「wazeroの薄いラッパー」に
過ぎない。ExecSandboxが汎用WASMランタイムのフロントエンドを超えて独自の価値を持つのは、
この2つの領域にこそある。

新設するケイパビリティは3つ（`send`／`recv`／`conn_write`）、ABI上は補助関数
`max_frame`を加えて4関数に収まる。外部接続対応で増えるケイパビリティが`conn_write`
ひとつで済んでいるのは、受信イベントをメールボックスに合流させた設計（4.3）の直接的な
効果である。

#### 使い勝手の改善はSDK側で行う

ABIは低レベルの契約であり、SDKライブラリはその上に言語ネイティブな皮を被せる。
「バッファ確保を利用者から隠す」「`kind`を列挙型にする」「タイムアウトを
`time.Duration`で受ける」といったことはすべてSDKの仕事であり、ABIには持ち込まない。

## 6. ビルド

### 6.1 コマンド

```
execsandbox-build -o <出力ファイル名> [--target <GOOS>/<GOARCH>] <入力.wasm>
```

- `--target`省略時は、ビルダーが動作しているプラットフォームを対象とする。
- ビルダーはサンドボックスポリシーを一切埋め込まない。ポリシーはすべて起動時に指定
  する。

#### ビルド時にポリシーを焼き込まない理由

ビルド時にマウント許可やメモリ上限を焼き込み、起動時はその範囲内でしか指定できない
「天井」とする案も検討したが不採用とした。

- 「隔離を決めるのは起動する側である」という原則（3.3）に例外を作らずに済む。ビルドは
  配布の形を作る行為であって隔離を決める行為ではない、という切り分けが貫ける。
- 起動時の配線（宛先の割り当て、待ち受けアドレス）を焼き込むと、同じWASMモジュールを
  別のシステム構成に転用できるという再利用性（3.3）が失われる。
- ビルダーの仕様が「入力：`.wasm`、出力：実行ファイル」の一行で済み、ポリシーの二重
  管理という複雑さが発生しない。

### 6.2 出力形式

```
[ベースバイナリ][WASMモジュール][フッタ]
```

フッタは固定32バイトとし、以下を含む。整数はビッグエンディアン。

```
Magic(8) + Version(4) + Offset(8) + Length(8) + Reserved(4)
```

実行時、ExecSandboxは自身のパスから自ファイルを読み、フッタを参照してWASMモジュールを
取り出す。マジックが一致しない場合はエラーを出力して起動を中止する。

#### スタンプ方式を選んだ理由

Goの`//go:embed`でユーザー側に`go build`させる案は、WASMモジュール開発者にGo
ツールチェーンを要求することになり、「どの言語で書かれていてもよい」という方針および
言語別開発キットの構想（2.1）と相性が悪い。スタンプ方式であればビルダーは単なる
ファイル結合であり、Rust開発者のキットにもそのまま同梱できる。

なお**ビルダー自身は6環境分のベースバイナリを`//go:embed`で内包する**。「ビルダーは
embed、生成物はスタンプ」という二層構造になる。

### 6.3 対応プラットフォーム

ビルダーは以下のベースバイナリを同梱する。

```
linux/amd64,   linux/arm64
darwin/amd64,  darwin/arm64
windows/amd64, windows/arm64
```

#### 同梱する理由

実行時にリリースから取得する方式は採らない。

- **バージョン不整合が原理的に起きない**：取得方式では「ビルダーv1.2が本体v1.1を
  落としてくる」状態がありうるが、同梱ならビルダーのバージョン＝生成される実行
  ファイルのバージョンで必ず一致する。サイズよりこちらが主な理由。
- ネットワーク不要でオフライン環境やCIでそのまま動く。

代償はビルダーのサイズで、1つ10MB前後×6プラットフォームで50MB規模になる。取得の
失敗やバージョン管理の複雑さが消えることとのトレードオフを受け入れた。

`windows/arm64`まで含めたのは、Snapdragon X系のCopilot+ PCという実機が存在し、Goの
クロスコンパイル（cgo不要）で追加コストがほぼゼロであるため。同梱方式では対象の追加に
ビルダーの再リリースが必要になるため、最初から広めに持つ。

### 6.4 コード署名

生成される実行ファイルは未署名とする。macOS・Windowsでは初回起動時に警告が表示される
場合がある。

スタンプ（バイナリ末尾への追記）は既存のコード署名を壊す。署名はファイル全体のハッシュで
検証されるため、追記は改ざんと区別がつかない。

先行するExecDBが6環境向けの実行ファイルを未署名のままリリースして運用できており、
そこで署名が論点になっていないため、同じ前提に揃えた。必要になれば「スタンプ後に署名し
直す」タイミングが一箇所に確定しているため、後から対応できる。

## 7. 起動時CLI仕様

```
<実行ファイル> [オプション...] [-- WASMへの引数...]
```

WASMモジュールは埋め込み済みのため、モジュールを指定する引数は存在しない。

各オプションの詳細な書式・使用例は `../usage/execsandbox.md` を参照。

### 7.1 オプション

| 短 | 長 | 引数 | 内容 | 既定値 |
|---|---|---|---|---|
| `-n` | `--name` | `ID` | 自身のID | なし（受信しない） |
| `-d` | `--dest` | `N=ID` | 宛先番号への割り当て。繰り返し可 | なし |
| `-e` | `--env` | `KEY=VALUE` | 環境変数。繰り返し可 | なし |
| `-v` | `--volume` | `HOST:GUEST[:ro]` | ディレクトリのマウント。繰り返し可 | なし（アクセス不可） |
| `-m` | `--mem-limit` | サイズ | WASM線形メモリの上限 | `512M` |
| `-b` | `--mailbox-limit` | 整数 | メールボックスの通数上限 | `1024` |
| `-f` | `--max-frame` | サイズ | 1通の最大バイト数 | `1M` |
| `-l` | `--listen` | アドレス | 外部接続の待ち受け。1つのみ | なし（待ち受けない） |
| `-s` | `--stdio` | ストリーム列挙 | 外部に接続するストリーム | なし（すべて遮断） |
| `-t` | `--timeout` | 期間 | 実行時間制限 | なし（無期限） |
| `-x` | `--deny` | 項目列挙 | 機能の遮断 | なし（すべて許可） |
| `-q` | `--quiet` | — | ホスト側ログの抑制 | 出力する |
| `-h` | `--help` | — | ヘルプ | — |
| `-V` | `--version` | — | バージョン | — |

短縮形と長形は必ずセットで用意する。`-h`は`--help`の定位置として予約。`-v`はマウント
（Dockerと同じ割り当て）であり、verboseではない。バージョンは`-V`。

**短縮フラグは小文字を原則とし、`-V`のみを例外とする。** `-v`をマウントに割り当てて
いる以上、バージョンは大文字に逃がすほかないため。それ以外は未使用の小文字から選ぶ
（`--deny`に`-x`を割り当てているのはこの方針による）。

### 7.2 `--`

`--`以降のすべての引数を、WASMモジュールへの引数（WASIの`WithArgs`）として渡す。

POSIX/GNU標準の記法であり、Goの`flag`パッケージも標準で終端として扱う。`-`単独はUnixで
「標準入出力をファイルとして指す」慣習が強く、stdioのオプションと衝突するため採用しない。

### 7.3 サイズの表記

`-m`および`-f`のサイズは以下の規則で解釈する。

- 接尾辞`K`／`M`／`G`は1024の冪を表す（`1M` = 1,048,576）。
- 大文字・小文字を区別しない。
- `Ki`／`Mi`／`Gi`も同値として受理する。
- 接尾辞のない数値はバイト数とする。

SI接頭辞としては1000の冪が本来の意味だが、メモリの文脈では1024の冪と解釈するツールが
多数派（Docker、JVM、`dd`等）であるため。大文字小文字を区別しないのはDockerが小文字、
Kubernetesが大文字という現状に対応するため。`Ki`/`Mi`/`Gi`も受理するのはKubernetesの
manifestから値をコピーする場合に備えたもの。

### 7.4 `-l, --listen` の書式

| 記述 | 待ち受け |
|---|---|
| `5432` | `127.0.0.1:5432` |
| `127.0.0.1:5432` | 同上 |
| `192.168.1.10:5432` | 指定インターフェースのみ |
| `:5432` | 全インターフェース |
| `[::1]:5432` | IPv6ループバック |
| `/run/mydb.sock` | Unixドメインソケット |

- ポート番号のみを指定した場合、ループバックアドレスを補完する（4.1）。
- 先頭がスラッシュの場合、Unixドメインソケットとみなす。`unix:`接頭辞も受理する。
- ホスト部が指定するのは待ち受けるインターフェースであり、接続元の制限ではない。

nginxの`listen`が持つ`default_server`・`ssl`・`http2`・`backlog=`といった修飾子は採用
しない。仮想ホストの概念がなく、TLSやプロトコルの解釈はゲストの責務であるため。

### 7.5 `-s, --stdio`

外部（シェル）に接続するストリームを列挙する。カンマ区切り。

| 値 | 対象 |
|---|---|
| `in` | 標準入力 |
| `out` | 標準出力 |
| `err` | 標準エラー出力 |
| `all` | 上記すべて |

指定しないストリームは`io.Discard`に接続される。

ファイルパスは受け付けない。出力先の振り分けはシェルのリダイレクトで行うほうが自然で
あり、値としてのファイルパスを許すと「`-`＝標準入出力」という記法が必要になって7.2の
議論に逆戻りするため。

### 7.6 `-x, --deny`

| 値 | 遮断対象 |
|---|---|
| `random` | 乱数生成 |
| `time` | 時刻取得 |

複数指定はカンマ区切り。

### 7.7 ホスト側ログ

ExecSandbox本体が出力するログは標準エラー出力へ書き出し、`execsandbox:`を接頭辞と
する。ゲストのstderrとは区別する。`-q`で抑制できる。

両者が同じ端末に流れたとき、どちらが出したものか判別できなくなるため接頭辞を付ける。
既定値が逆である点にも注意する。ホスト側ログは既定で出力し、ゲストのstderrは既定で
遮断する。ゲスト側は明示的に配線しない限り何もできないというケイパビリティの原則に
従う一方、ホスト側は運用者が見るべき情報だからである。

標準出力はゲストのものであり、ホストは使わない（`--version`・`--help`のみ例外）。
ホストがstdoutに書くと、ゲストの出力に混ざって利用者のパイプ処理を壊す。

**ホストの出力（ログ、エラーメッセージ、`--help`・`--version`）はすべて英語とする。**
CLIの出力は`grep`やパイプ、ログ収集基盤を通る機械的な対象であり、またissue等に貼られて
第三者が読むものだからである。利用者が特定の言語の話者とは限らない以上、ドキュメントとは
扱いを分ける。

## 8. サンドボックスポリシー

以下はすべて起動時オプションで指定する。指定しない項目は既定値が適用される。

| 項目 | 実装 | 既定 |
|---|---|---|
| ファイルシステム | `WithFSConfig` | アクセス不可 |
| 標準入出力 | `WithStdin`／`WithStdout`／`WithStderr` | すべて遮断 |
| 環境変数・引数 | `WithEnv`／`WithArgs` | なし |
| メモリ上限 | `WithMemoryLimitPages` | `512M` |
| 実行時間 | `context.WithTimeout` | 無期限 |
| 乱数・時刻 | `WithRandSource`／`WithWalltime`／`WithNanotime` | 許可 |
| サンドボックス間通信 | 独自実装 | 宛先未割り当て |
| 外部接続 | 独自実装 | 待ち受けなし |

乱数・時刻を除き、明示的に指定しない限り利用できない（ホワイトリスト方式）。乱数・
時刻のみ既定で許可とするのは、ホストの機密情報を漏らすリスクが低いため。

実行時間制限を既定で無効とするのは、`recv()`で待ち続けるループ等、無期限稼働を前提と
する常駐サンドボックスが基本の実行モデルであるため。一時的なバッチ処理用途向けの
オプトイン機能として位置づける。

### 8.1 既定値の考え方

| オプション | 既定値 | 根拠 |
|---|---|---|
| `-m` | `512M` | wasm32の上限（4GiB、実際は多くのツールチェーンで2GiB前後が頭打ち）に対して十分な余裕がある位置。SQLite相当のモジュールを載せても窮屈にならず、暴走時には早めに止まる |
| `-f` | `1M` | SQL文やJSONのやり取りには十分すぎる広さ。1MBを超える1通は既に異常な部類 |
| `-b` | `1024` | `-f`との積（1M × 1024 = 1G）がメールボックス側のメモリ上界となる。fan-inのバーストを吸収できる深さ |

**これらは上界であって確保量ではない。** WASMの線形メモリは必要に応じて伸び、
メールボックスも実際に溜まった分しかメモリを消費しない。アイドル時の実フットプリントは
Goランタイム込みで数MB程度であり、既定値を余裕側に振っても通常運用のメモリ消費は
増えない。効くのは「暴走時にどこで止まるか」だけである。

プロセス全体のメモリ上界は、WASM側（`-m`）とホスト側のメールボックス（`-b`×`-f`）が
別枠であるため概ねその合計となる。既定値では 512M + 1G ≒ 1.5G。

用途に応じて深さと1通のサイズは入れ替えられる。小さいメッセージが大量に流れる構成なら
`-f 64K -b 16384`とすることで、同じ1Gの上界のまま深さを16倍にできる。

## 9. 制限事項

以下はv1のスコープ外とした。いずれも既存の設計を壊さずに追加できる形にしてある。

| 事項 | 追加する場合の形 |
|---|---|
| 別マシンをまたぐ分散対応（3.1） | 宛先IDの解決先をUnixドメインソケットからTCPへ広げる |
| Windowsでの名前付きパイプ（3.1） | Windows固有の問題が顕在化した時点で`go-winio`等による分岐を追加 |
| アウトバウンド接続（4.4） | 起動時に接続先を許可リストで固定し、ゲストは番号で選ぶ |
| 接続元IPによるフィルタ（4.4） | — （OSの仕組みに委ねる） |
| 複数の待ち受け口（4.1） | イベントのメタデータにリスナー番号を追加 |
| 接続元アドレスの受け渡し（4.4） | `conn_peer(conn_id, ptr, cap) -> i32`を追加 |
| stdinのメールボックスへの合流（4.3） | 起動時オプションで配線を選べるようにする |
| リッチな端末制御（raw mode、履歴、補完、割り込み） | — |
| 管理用の外部インターフェース（2.2） | — （管理役のExecSandboxで表現する） |
| 複数プロセスの管理機構（2.2） | — （supervisord等に委ねる） |
| コード署名（6.4） | ビルダーのオプションとして追加 |
